## 优化项

### [OPT-001] brainstorm 意图分类改用 function call

**问题描述**

用户确认设计方案后，系统一直输出新的确认单而不生成代码。

**根本原因**

`_classify_brainstorm_response()` 调用 LLM 判断用户意图时，依赖文本匹配（找 `CONFIRM` / `REVISE` / `ABORT` 关键词），兜底逻辑是 `revise`。当 LLM 返回中文或格式不规范时，匹配失败默认走 revise，触发新一轮确认单，陷入循环。

**当前修复**（已上线）

- 加了关键词快速判断，用户说"好的/可以/确认/开始"等直接走 confirm，不经过 LLM
- 兜底逻辑从 `revise` 改为 `confirm`，避免死循环

**优化方向**

改用 function call（tool use），模型被强制返回 enum 值，彻底消除格式解析问题：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "classify_intent",
        "parameters": {
            "type": "object",
            "properties": {
                "intent": {"type": "string", "enum": ["confirm", "revise", "abort"]}
            },
            "required": ["intent"]
        }
    }
}]
```

**前提条件**

租户配置的模型需支持 function call。部分国产模型（如 Qwen 某些版本）支持度不一致，需做兼容降级处理（不支持时回退到当前关键词方案）。

**相关文件**

- `backend/app/coding/pipeline.py` — `_classify_brainstorm_response()` / `_brainstorm_llm_call()`

## OPT-002 serve 进程堆积问题

**状态：** ✅ 已修复（2026-04-13）

**优先级：** 🔴 必须做（已解决）

**问题描述**

用户在 code-server 终端执行 `npm run serve` 后，关闭浏览器标签页不会 kill 掉服务器上的 serve 进程。平台为多用户系统，每个用户可能有多个工作区，每次执行 `npm run serve` 都会占用一个端口，时间长了会导致：

- 服务器端口耗尽（可用端口范围有限，如 8082-9000 约 918 个）
- 大量僵尸进程占用系统资源
- 新工作区无法分配到可用端口

**修复内容**

- `main.py`：lifespan 启动时 `pkill -f vibe-serve.js`，清理上次后端退出残留的孤儿进程
- 同一工作区单例已由 `WorkspaceManager._serve_processes` + `is_serve_running` 保证（原有逻辑）
- 顺手修复 `workspace.py` 中一处 `vibe-serve-config` 写入用了双花括号导致 `PROXY_BASE` 未被正确求值的历史 bug

**效果**

- 后端重启 → 自动 kill 所有残留 serve 进程，状态干净
- 同一工作区多次 `npm run serve` → 复用已有进程，不重复启动

**相关文件**

- `backend/templates/cli-generated/form-component-web/vibe-serve.js`
- `backend/app/coding/workspace.py` — `WorkspaceManager._serve_processes`
- `backend/app/coding/tools.py` — `_start_serve()`

## FIX-001 serve_started 事件被 harness 适配层静默丢弃

**状态：** ✅ 已修复（2026-04-12）

**问题描述**

`start_serve` 工具执行成功后，`vibe_agent.py` 会发出 `{"type": "serve_started", "url": "..."}` 事件，前端用此事件调用 `window.__apaasDebug?.addRecord(url)` 注入调试扩展。但前端始终收不到该事件。

**根本原因**

前端通过 harness 接口消费事件，事件流经过如下链路：

```
vibe_agent._emit(serve_started)
  → pipeline.py yield event
    → CodingProfile.run_turn()  ← ❌ 此处无 serve_started 分支，事件静默丢弃
      → EventBus.publish()
        → HarnessManager
          → CodingSSEAdapter.translate()
            → SSE → 前端
```

`CodingProfile.run_turn()` 通过 `if/elif` 链处理各事件类型，`serve_started` 没有对应分支，直接跳过，从未发布到 EventBus。

**修复**

在 `backend/app/harness/profiles/coding.py` 的 `run_turn()` 中新增一个 `elif` 分支：

```python
elif event_type == "serve_started":
    await event_bus.publish(
        ITEM_DELTA, turn_ctx.turn_id,
        {"kind": "system", **event},
        item_kind="system", persist=False,
    )
```

走 `kind=system` 路径，`CodingSSEAdapter` 的 system 透传逻辑会将 `type=serve_started` 原样转发给前端。

**注意点**

- 修改是纯新增 `elif` 分支，不影响任何已有事件类型的处理逻辑
- 新增事件类型（如后续的 `build_started`、`test_result` 等）同理：必须在 `CodingProfile.run_turn()` 中显式添加分支，否则会被静默丢弃
- `persist=False` 表示不写数据库，仅实时推送

**相关文件**

- `backend/app/harness/profiles/coding.py` — `CodingProfile.run_turn()`
- `backend/app/harness/sse_adapter.py` — `CodingSSEAdapter.translate()`（`kind=system` 透传逻辑）
