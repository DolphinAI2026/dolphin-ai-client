## 优化项

### [OPT-001] brainstorm 意图分类改用 function call

**问题描述**

用户确认设计方案后，系统一直输出新的确认单而不生成代码。

**根本原因**

`_classify_brainstorm_response()` 调用 LLM 判断用户意图时，依赖文本匹配（找 `CONFIRM` / `REVISE` / `ABORT` 关键词），兜底逻辑是 `revise`。当 LLM 返回中文或格式不规范时，匹配失败默认走 revise，触发新一轮确认单，陷入循环。

**当前修复**（已上线）

- 加了关键词快速判断，用户说"好的/可以/确认/开始"等直接走 confirm，不经过 LLM
- 兜底逻辑从 `revise` 改为 `confirm`，避免死循环

**优化方向**

改用 function call（tool use），模型被强制返回 enum 值，彻底消除格式解析问题：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "classify_intent",
        "parameters": {
            "type": "object",
            "properties": {
                "intent": {"type": "string", "enum": ["confirm", "revise", "abort"]}
            },
            "required": ["intent"]
        }
    }
}]
```

**前提条件**

租户配置的模型需支持 function call。部分国产模型（如 Qwen 某些版本）支持度不一致，需做兼容降级处理（不支持时回退到当前关键词方案）。

**相关文件**

- `backend/app/coding/pipeline.py` — `_classify_brainstorm_response()` / `_brainstorm_llm_call()`

## [必须优化] OPT-002 serve 进程堆积问题

**优先级：** 🔴 必须做

**问题描述**

用户在 code-server 终端执行 `npm run serve` 后，关闭浏览器标签页不会 kill 掉服务器上的 serve 进程。平台为多用户系统，每个用户可能有多个工作区，每次执行 `npm run serve` 都会占用一个端口，时间长了会导致：

- 服务器端口耗尽（可用端口范围有限，如 8082-9000 约 918 个）
- 大量僵尸进程占用系统资源
- 新工作区无法分配到可用端口

**方案：心跳 + 后端统一管理**

1. **`vibe-serve.js` 启动后每 30 秒向后端发一次心跳**，携带工作区 ID 和 PID
2. **后端维护进程表**：`{ ws_id: { pid, port, last_ping } }`，持久化到内存或 SQLite
3. **后端定时任务**（每 5 分钟跑一次），把超过 10 分钟没心跳的进程 kill 掉，释放端口
4. **启动时去重**：`vibe-serve.js` 启动前先问后端「这个工作区有没有在跑的 serve」，有的话复用端口，不重新启动

**改动点**

- `vibe-serve.js`：加入心跳逻辑，启动时向后端注册，退出时注销
- 后端：新增进程管理模块，维护进程表 + 定时清理任务

**效果**

- 用户关浏览器 → 心跳停止 → 10 分钟后自动回收
- 同一工作区多次 `npm run serve` → 复用已有进程，不重复启动
- 多用户并发 → 后端统一管控端口分配，不会冲突

**相关文件**

- `backend/templates/cli-generated/form-component-web/vibe-serve.js`
- `backend/app/coding/workspace.py` — `_VIBE_SERVE_JS` 常量
