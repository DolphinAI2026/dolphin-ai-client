# 桌面 Code 统一应用与本地项目初始化体验设计

**Spec ID**：`2026-07-28-desktop-code-local-remote-application-experience`
**日期**：2026-07-28
**修订日期**：2026-08-14
**状态**：交互方案已确认，待原型修订
**工程**：`apaas-builder-ai`

## 1. 背景

旧设计将本地应用和远程应用作为两套完全分离的页面与生命周期。实际使用中，用户管理的是同一个 Code 应用；本机目录和远程工作区只是该应用可以打开和运行的位置。未来同一应用可能同时拥有本机副本和远程副本，并通过尚未确定的机制同步。完全分离导致以下问题：

1. 用户需要先判断来源，才能找到应用或决定从哪个入口创建。
2. “新建本地应用”只能创建新目录，无法接入已经存在的项目。
3. 已有项目注册后只得到一个空工作台，没有项目识别、下一步建议或首个有效会话。
4. 本地和远程需要独立处理加载失败，但不应因此表现成两套产品。
5. 如果把本地或远程直接定义成应用来源，未来建立副本关联和同步后会出现重复应用、入口迁移和会话归属歧义。

本次修订废弃“本地应用与远程应用是两个独立产品分区”的交互结论，改为统一应用对象、多个可用位置和独立运行边界。同步机制本轮不实现，但当前信息架构不得阻碍后续增加同步能力。

## 2. 目标

- Code 应用页按逻辑应用统一展示，每个应用最多出现一次。
- 本机、远程只作为应用的可用位置，不再作为应用类型或两个互斥页面。
- 一个应用可以仅有本机位置、仅有远程位置，或同时具备两种位置。
- 会话仍是进入应用后的核心操作对象，但不会承担本机和远程位置切换。
- 桌面端能够创建新项目，也能直接选择已有项目目录。
- 接入已有项目时默认执行安全、只读的项目识别。
- 首次接入自动创建并运行“项目初始化”会话，让用户直接获得项目现状和下一步建议。
- 不要求已有目录是 Git 仓库，不自动安装依赖，不修改源码和工程配置。
- 本地与远程继续保持独立的数据请求和错误边界，任一来源失败不阻断另一来源。

## 3. 统一应用与位置模型

### 3.1 概念边界

- `应用`是稳定的逻辑身份，承载名称、编码和会话归属。
- `本机位置`指应用绑定的本机项目目录。
- `远程位置`指应用绑定的远程工作区或远程副本。
- `运行位置`指用户本次从哪个位置打开应用，不表示会话可以在运行中切换位置。
- `同步状态`描述本机和远程副本之间的关系，不与运行位置混用。
- 只有服务端稳定标识或用户明确建立关联时，两个位置才能合并为同一个应用；不得仅凭同名目录或应用名称自动合并。

### 3.2 展示方式

- 桌面 Code 应用页默认展示全部应用。
- 原来的`本地应用 | 远程应用`主分段控件改为位置筛选：`全部`、`本机可用`、`远程可用`。
- 每个逻辑应用只展示一条记录，在记录内展示其可用位置和同步状态。
- 本机位置展示项目目录最后一级名称，悬停显示完整路径。
- 远程位置展示所属租户、环境或远程工作区名称。
- 同时存在两个位置时，不重复显示应用；位置并排展示，主按钮使用上次打开位置，其他位置放入按钮下拉菜单。
- 仅有本机位置时，主操作为`在本机打开`。
- 仅有远程位置时，主操作为`在远程打开`；`创建本机副本`放入次级操作，不强制先下载到本机。
- 同步能力尚未建立时，只显示`仅在本机`、`仅在远程`或`本机与远程已关联`等真实状态，不展示虚假的同步进度。
- 搜索、状态筛选、列表/卡片切换和分页对统一结果生效。
- Web 端没有本机目录能力，只允许从远程位置打开，但仍使用同一个逻辑应用模型。

### 3.3 工作台表达

- 进入应用后，左侧主要展示该应用的会话列表，不再重复展示一套应用管理列表。
- 工作台顶部展示应用名称、当前运行位置和同步状态入口。
- 输入框附近以简短文本显示当前运行位置，例如`本机 · CRM`或`远程 · 开发环境`。
- 当前会话不提供本机/远程切换控件。用户需要换位置时，从应用入口选择另一个位置打开。
- 同步状态使用低干扰图标或文本入口，不占用对话主区域；只有冲突或阻断当前操作时才展示页内横幅。

### 3.4 加载与错误隔离

本地和远程仍分别请求和维护状态，页面再合并结果：

- 本地加载失败时，已经加载成功的远程应用继续显示。
- 远程加载失败时，已经加载成功的本地应用继续显示。
- 单一来源失败使用页内横幅提示，不把整个列表替换成错误页。
- 只有两个来源都不可用时才显示全页错误状态。
- 刷新操作分别重试失败来源，不清空已经成功的数据。

## 4. 添加应用入口

桌面端使用一个主操作“添加应用”，展开三个明确入口：

1. `新建本地项目`
2. `打开已有项目`
3. `添加远程应用`

Web 端只显示`添加远程应用`，不显示不可用的本机入口。

### 4.1 新建本地项目

- 用户填写应用名称。
- 应用编码自动生成，创建前允许编辑，创建后只读。
- 用户选择保存位置，最终目录为`<保存位置>/<应用编码>`。
- 创建目录、注册应用后创建首个普通 Code 会话并进入工作台。
- 本轮不自动生成技术栈脚手架；用户进入会话后再说明要创建的应用。

### 4.2 打开已有项目

- 系统目录选择器直接选择项目目录本身，不再把选择结果当作父目录并拼接应用编码。
- 应用名称默认取目录最后一级名称，创建前允许编辑。
- 应用编码根据目录名称生成，创建前允许编辑，注册后只读。
- 显示默认开启的`初始化项目`复选框。
- 明确说明初始化只会建立 Dolphin Code 注册信息、识别项目并创建初始化会话，不会修改源码、Git 或依赖。
- 不要求目录是 Git 顶层目录，也不要求目录已经执行过 Git 初始化。

### 4.3 仅有远程位置时创建本机副本

远程应用的主操作仍为`在远程打开`。用户从次级菜单选择`创建本机副本`后，使用单个侧边面板完成：

1. 选择本机根目录。
2. 预览最终目录，例如`D:\DolphinCode\crm`。
3. 展示即将获取的应用及目标位置，不承诺尚未确定的同步协议。
4. 创建本机副本、注册本机位置并执行安全的只读项目初始化。
5. 完成后在本机打开该应用。

创建失败时保留远程位置和原应用记录。未完成的本机目录不得直接注册为可用位置；可以提供清理或重试入口。

### 4.4 仅有本机位置时创建远程副本

用户从本机应用的次级菜单选择`创建远程副本`后：

1. 选择远程环境或工作区。
2. 确认远程应用名称和编码。
3. 展示准备发送的内容、忽略项和目标位置。
4. 创建远程副本并建立应用位置关联。
5. 完成后提供`留在本机`和`在远程打开`两个清晰结果动作。

同步协议未确定前，该流程在产品中可以显示为预留能力或禁用入口，但原型必须展示完整的未来交互，不模拟已经成功同步。

## 5. 已有项目初始化

### 5.1 初始化边界

初始化采用已确认的安全模式：

- 注册本地应用与工作区。
- 将客户端和 Runtime 所需的注册、会话元数据写入桌面数据目录。
- 只读识别项目结构和技术栈。
- 创建并运行首个`项目初始化`会话。
- 不修改项目源码、Git 状态、依赖清单、锁文件、README 或`.gitignore`。
- 不执行依赖安装、数据库迁移、构建、测试或启动命令。
- 后续任何文件修改或命令执行都必须在会话中由用户明确提出或确认。

### 5.2 轻量识别

识别阶段只读取能判断项目现状的少量信息：

- 顶层目录和有限深度的目录结构。
- `README`、`AGENTS.md`及已有项目说明。
- 常见清单和锁文件，例如`package.json`、`pyproject.toml`、`pom.xml`、`Cargo.toml`、`go.mod`。
- 常见启动、构建、测试脚本和入口文件。
- Git 是否存在、当前分支和工作区状态；Git 仅作为信息，不作为接入条件。
- 当前电脑是否具备项目声明的关键运行环境。

默认跳过`.git`、`node_modules`、`.venv`、`vendor`、`target`、`dist`、`build`、缓存目录、二进制文件和大型文件。识别失败不回滚应用注册，用户仍可进入工作台手动处理。

### 5.3 初始化会话

注册成功后必须创建一个新的 Code 会话，不能复用该应用已有的最近会话：

- 会话标题固定为`项目初始化`；同一应用后续重复检查使用`重新检查项目`。
- 会话用途记录为项目初始化，便于防止重复发送初始任务。
- 工作台完成 readiness 后，宿主只发送一次初始化任务。
- 初始化任务要求 Agent 先只读分析，不执行修改和安装命令。
- 页面直接进入该会话，并显示正常的本地工作台加载阶段。

初始化回复至少包含：

1. 项目用途和主要技术栈。
2. 已识别的目录、入口和模块。
3. 可用的启动、构建和测试命令，仅展示，不自动执行。
4. 缺失的本机环境、配置或凭据。
5. 当前项目可运行程度和明显风险。
6. 推荐的下一项操作，并等待用户决定是否执行。

## 6. 数据流与接口调整

### 6.1 应用列表

- 前端并行请求本机和远程位置，再按稳定应用标识或显式关联关系合并为逻辑应用。
- 本机位置继续来自桌面 Builder 的本地注册存储。
- 远程位置继续来自当前远程服务和租户上下文。
- 同名应用没有稳定关联标识时保持独立，并提示用户可以在未来手动关联，不自动覆盖或合并。
- 不用本地 SQLite 租户模拟远程应用，也不让远程失败清空本地数据。

### 6.2 本地应用注册

本地应用创建请求增加明确的目录模式：

- `new_directory`：后端创建最终项目目录。
- `existing_directory`：目录必须已经存在且可读，后端直接注册该目录。

后端使用规范化绝对路径检查重复注册。同一用户重复选择同一路径时不创建第二个应用，而是返回已有应用及`already_registered`状态。

### 6.3 会话创建

现有外部应用会话接口默认会复用最近会话，不能满足初始化要求。接口需要增加显式的新建语义，或提供专用初始化会话入口，保证：

- 首次接入创建新的`项目初始化`会话。
- 普通点击应用仍可沿用现有会话恢复策略。
- 初始化任务具有幂等键，同一初始化会话只自动发送一次。
- iframe readiness 之前不发送任务，避免消息丢失或重复执行。

## 7. 重复接入与恢复

- 同一路径已经注册：不创建重复应用，打开已有应用。
- 已注册但没有会话：创建`项目初始化`会话。
- 已有初始化会话且尚未完成：恢复该会话，不重复发送任务。
- 已完成初始化：打开最近会话，并提供`重新检查项目`操作；该操作创建新会话，不覆盖历史结果。
- 目录已移动或不可读：保留应用记录，在当前页面提供`重新选择目录`。
- 本机目录失效且存在远程位置：提供`重新定位目录`、`从远程恢复到本机`和`移除失效位置`，远程打开不受影响。
- 远程位置暂时不可用且存在本机位置：继续允许在本机打开，并提供远程重试入口。
- 两个位置存在未同步修改：显示`有更新待同步`，但不自动选择覆盖方向。
- 检测到同步冲突：禁止静默覆盖，提供独立冲突处理入口；冲突不阻止用户以只读方式查看现有位置。
- 发现疑似同一应用：保持两个独立应用，只有用户确认后才建立关联。
- Runtime 启动失败：保留应用和会话，用户重试时继续原初始化会话。
- 模型不可用：应用注册仍成功，在会话区域显示可恢复提示，不删除项目或元数据。

## 8. 工作台加载体验

本地项目仍沿用三个真实阶段：

1. 检查本地项目。
2. 启动本地环境。
3. 打开 Code 工作台。

初始化任务只能在工作台发出 readiness 后开始。加载、识别和初始化状态留在应用窗口内，不弹命令行窗口，不跳回登录页，不用多个 Toast 重复报告同一过程。

远程位置继续使用远程工作区加载流程，但统一使用相同的页面级加载视觉，不把应用列表和工作台 iframe 加载状态混为一体。

## 9. 验收标准

- 桌面 Code 应用页首次进入按逻辑应用展示统一列表，同一应用的两个位置不会生成两条记录。
- 位置筛选可以显示全部、本机可用或远程可用，应用记录清晰展示可用位置。
- 仅有远程位置的应用点击主操作时直接远程打开，创建本机副本位于次级菜单。
- 仅有本机位置的应用可以从次级菜单进入创建远程副本流程。
- 同时具备两个位置的应用使用上次打开位置作为主操作，并允许从下拉菜单选择另一位置。
- 工作台以会话为核心，仅显示当前运行位置，不提供会话中的位置切换控件。
- 本机路径失效、远程不可用、待同步和冲突状态都有明确且不破坏另一位置的恢复入口。
- 一个来源加载失败时，另一个来源仍能使用。
- “添加应用”能够选择新建本地项目、打开已有项目或添加远程应用。
- 选择已有目录时，最终工作区就是所选目录，不额外拼接子目录。
- 非 Git 目录可以成功注册和打开。
- 默认勾选初始化项目，说明文字明确不会修改源码、Git 和依赖。
- 首次接入已有项目后创建新的`项目初始化`会话，不复用旧会话。
- 工作台就绪后自动运行一次只读初始化任务，并输出项目识别结果和下一步建议。
- 初始化过程中不安装依赖、不执行构建、不修改项目文件。
- 重复选择同一路径不会产生重复应用或重复初始化任务。
- 识别、Runtime 或模型失败后，应用与会话仍可恢复。
- 整个流程不出现命令行黑框、登录循环或无解释空白页。

## 10. 聚焦验证

- 本地应用表单：新建目录和已有目录两种模式的路径语义。
- 本地注册服务：非 Git 目录、重复路径、不可读路径。
- 应用列表：位置按稳定身份合并、位置筛选、同名未关联及单位置失败。
- 应用位置：仅本机、仅远程、双位置、本机目录失效、远程不可用和冲突状态。
- 会话服务：强制新建初始化会话和幂等初始任务。
- 工作台桥接：仅在 readiness 后发送一次初始化任务。
- 不新增无关的大范围测试，不重新验证未受影响的 Builder 功能。

## 11. 非目标

- 不实现本机与远程副本的实际传输、增量同步、冲突合并或版本协议；本轮只冻结兼容未来同步的交互和状态边界。
- 不自动生成项目脚手架。
- 不自动初始化 Git、提交代码或关联远程仓库。
- 不自动安装依赖、启动服务、构建或测试。
- 不重做 Code 内层编辑器和 Agent 执行引擎。
- 不用 mock 替代真实目录注册与本地 Runtime。
