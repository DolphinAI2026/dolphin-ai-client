# 桌面账号管理端 — 需求 & 指标建议

> 给设计(Claude design)的输入文档。描述 account-service 管理端的**完整形态**(当前只实现了最小的开号/改密/停用),以及运营该看哪些指标。
>
> 日期:2026-06-16 · 关联:`docs/superpowers/specs/2026-06-16-account-service-design.md`

---

## 1. 背景与定位

account-service 是桌面交付驾驶舱的**桌面账号权威**(独立服务,公网部署在 `agent.dfy.definesys.cn/account-api`)。桌面端通过 federation 连它登录,新机器不用复制账号库。

**管理端**是给平台管理员/运营用的 Web 控制台,干两件事:
1. **管账号** —— 开号、停用、改密、查账号、管权限。
2. **看运营** —— 账号规模、活跃度、登录健康、安全信号。

当前实现只有第 1 件的最小集(开号/改密/停用/列表)。本文描述完整形态。

---

## 2. 用户与典型场景

| 角色 | 能做什么 | 典型场景 |
|---|---|---|
| 平台管理员(超管) | 管所有账号、看全局指标、配策略 | 给新同事开号 / 停掉离职的 / 排查"某人登不上" / 看整体活跃和增长 |
| 团队/租户管理员(未来) | 管自己团队的成员 | 部门负责人自助管本部门账号 |

日常高频动作:**开号**、**停用离职**、**帮人重置密码**、**排查登录失败**、**看本周有多少人在用**。设计要让这几件事顺手。

## 3. 信息架构(页面)

```
管理端
├── 概览 Dashboard      ← 指标看板(§6)
├── 账号管理            ← 列表 + 详情(核心)
├── 租户管理            ← 列租户 / 详情(未来)

└── 设置                ← 密码策略 / 会话TTL / SSO(未来)
```

## 4. 功能需求(按模块)

### 4.1 概览 Dashboard
进来第一眼看到的运营快照:顶部一排 KPI 卡(总账号 / 活跃 / 今日登录 / 新增),下面趋势图(登录趋势、新增趋势)+ 几个分布(状态、角色)。具体指标见 §6。

### 4.2 账号管理(核心)
**列表**
- 搜索:按用户名。
- 筛选:状态(启用/停用)、角色(管理员/普通)、租户、注册时间区间、最近活跃(N 天内/沉睡)。
- 列:用户名、所属租户、状态、角色、注册时间、**最后登录时间**、**登录设备数**。
- 排序、分页、每页条数。
- 批量选择 → 批量停用/启用。

**单账号操作**
- 开号(单个表单 + 批量:CSV 导入或多行)。
- 停用 / 启用(停用要提示"已登录设备多久失效",见 §7 吊销)。
- 重置密码(管理员设新密码,或生成临时密码让用户首次登录改)。
- 设为管理员 / 取消管理员。
- 删除(软删,保留审计;不建议硬删)。
- 查看详情。

**账号详情**
- 基本信息:用户名、租户、角色、状态、注册时间、最后登录。
- **登录历史**:时间、来源 IP、设备/机器标识、结果(成功/失败+原因)。
- **当前活跃会话/设备**:这个账号现在在哪几台机器上登录着,可**强制下线**某台。

### 4.3 租户管理(未来)
列租户、租户详情(成员、配额、绑定的 aPaaS 环境)。桌面账号目前是「一人一私有租户」,租户管理优先级低,先放后面。

### 4.4 登录日志 / 操作审计
- **登录日志**:每次登录(含 federation 转发)记一条 —— 账号、时间、IP、设备、结果、失败原因。可按账号/时间/结果筛。
- **操作审计**:管理员每个动作记一条 —— 谁(actor)在什么时候对谁(target)做了什么(开号/停用/改密/改权限)。合规和追责用。

### 4.5 设置(未来)
- 密码策略:最小长度、复杂度、有效期。
- 会话:token TTL、吊销策略(停用后多久全机失效,对应 spec 里的 revocation)。
- SSO:钉钉 / 企微接入。

## 5. 关键状态与交互(给设计提示)

- **停用确认弹窗**要说清后果:"该账号已登录的桌面端将在 ≤N 分钟内失效"(取决于吊销策略)。
- **重置密码**:两种模式 —— 管理员直接设 / 生成临时密码(展示一次,提示用户首次登录改)。
- **批量开号**:CSV 模板下载 + 上传 + 预览校验 + 逐条结果(成功/失败原因)。
- **空状态 / 加载 / 错误**:列表空、无搜索结果、加载骨架、接口失败重试,都要有像样的态。
- **权限可见性**:超管看全量;租户管理员(未来)只看自己租户,UI 要按角色裁剪。

## 6. 指标体系(运营看什么)— 重点

> 你特别问的"看哪些指标"。按这五组组织,Dashboard 选其中最关键的几个做 KPI 卡 + 趋势图。

### 6.1 账号规模(现状盘点)
- **总账号数**、启用数、停用数。
- **管理员数**。
- 各租户账号数 Top N。

### 6.2 活跃度(最该盯的)
- **DAU / WAU / MAU** —— 当日 / 近 7 天 / 近 30 天有过登录的账号数。
- **活跃率** = 活跃账号 / 总账号。
- **人均登录设备数** —— 一个账号在几台机器上登录(federation 镜像数),反映多机办公。
- **沉睡账号** —— N 天(如 30 天)没登录过的,可提醒清理。

### 6.3 登录健康(系统在不在好好工作)
- **登录次数趋势**(按日/周)。
- **登录成功率**;**失败次数 + 失败原因分布**(密码错 / 账号停用 / 公网账号服务不可达)。
- **federation 转发健康** —— 桌面连公网 authority 的成功率/延迟(503 不可达激增 = 公网账号服务有问题)。

### 6.4 增长
- **新增账号趋势**(日/周)。
- **净增** = 新增 − 停用。

### 6.5 安全信号(异常预警)
- **停用账号的登录尝试** —— 离职后还在试登录,值得关注。
- **异常登录** —— 同账号短时间多地/多设备、高频登录失败。
- **密码重置频率** —— 突增可能是钓鱼或账号问题。

## 7. 数据前提(要看指标,得先记)

⚠️ 当前 account-service **不记登录日志、不记操作日志**,所以 §6 的活跃度/登录健康/安全信号**现在拿不到数据**。Dashboard 之前必须先补两张表 + 埋点:

- **登录事件表** `login_events`:`account_id, ts, ip, device/instance_id, result(success/fail), fail_reason`。每次 `/login`(authority + federation)写一条。
- **操作审计表** `admin_audit`:`actor_id, action, target_username, ts, detail`。每个管理 API 写一条。

派生指标的算法:
- DAU/WAU/MAU、登录趋势、成功率、失败原因 → 从 `login_events` 聚合。
- 人均设备数、活跃会话 → 从 `login_events` 的 `device/instance_id` 去重统计(或下游 sidecar 上报)。
- 账号规模、新增/停用 → 从 `users` 表 + `created_at` / 状态变更(状态变更要 `admin_audit` 才准)。

**这是看板的前置后端工作,设计可以先按"指标都有数据"画,工程按这两张表实现埋点。**

## 8. 分期建议

| 阶段 | 内容 |
|---|---|
| **P0(已做)** | 开号 / 改密 / 停用 / 列账号 |
| **P1** | 账号列表搜索·筛选·分页 + 账号详情 + **登录事件埋点(login_events)** + 登录日志页 + 概览基础 KPI(总数/活跃/今日登录/新增) |
| **P2** | 完整指标看板(活跃度 DAU/WAU/MAU + 登录健康 + 安全信号 + 趋势图) + 操作审计(admin_audit)+ 批量开号 + 强制下线 |
| **P3** | 租户管理 + 设置(密码策略 / TTL / 吊销)+ SSO(钉钉/企微) |

设计可以先把 P1+P2 的页面画全(账号管理 + 概览看板 + 日志),那是管理端的主体。

## 9. 风格基调(给设计)

企业级后台:克制、信息密度合理、可长时间使用不累。参考成熟 admin(如 阿里云/腾讯云控制台、Linear settings、Vercel dashboard 的克制感),**不要花哨渐变、不要 AI slop**。表格是核心载体,要好读;KPI 卡和趋势图克制配色;操作按钮层级清晰(主操作实色、次操作幽灵/文字)。
