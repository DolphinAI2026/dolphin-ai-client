**分派**是按项目类型的，**校验规则**是共用的。两层结构：

---

**第一层：构建流程分派**（[workspace.py:1447-1451](.claude/worktrees/competent-chatterjee-6d4c33/backend/app/coding/workspace.py:1447)）

```python
if project_type == FORM_COMPONENT_DUAL:
    result = await self._build_dual_project(...)   # 两端分别 build + 两端分别验产物
else:
    result = await self._build_single_project(...) # 单端 build + 单端验产物
```

双端独特的地方：**跑两次 build**（`web/`、`mobile/` 各一次），**验两次产物**。

---

**第二层：产物目录定位**（[workspace.py:580-605](.claude/worktrees/competent-chatterjee-6d4c33/backend/app/coding/workspace.py:580)）—— 这一层确实按 project_type 走不同规则：

| 项目类型 | 产物目录 | 来源 |
|---|---|---|
| `form-component-dual` | `web/{outputName}/` + `mobile/{outputName}/` | `{side}/src/apaas.json.outputName` |
| `backend-api` / `backend-feign` / `backend-scheduled` | `target/` | 固定（Maven 约定） |
| `FORM_COMPONENT` template（单端）| `{outputName}/` | `src/apaas.json.outputName` |
| `MENU_PAGE` / `FORM_PAGE` / `PAGE_LAYOUT` / `LIST_VIEW` | `{outputName}/` | `src/apaas.json.outputName` |
| `FRONTEND_PLUGIN` / `PLUGIN` | 特殊逻辑 | `_get_frontend_plugin_output_dir` |
| **其他 / 默认兜底** | `dist/` | 硬编码 |

---

**第三层：产物内容校验 —— 统一一条规则**（[workspace.py:611-617](.claude/worktrees/competent-chatterjee-6d4c33/backend/app/coding/workspace.py:611)）

```python
def _has_build_artifacts(self, output_dir):
    return output_dir 存在 且 内部有任意 *.js / *.css / *.html / *.jar / *.war 文件
```

**无论什么项目类型，内容校验都跑同一套规则**。只要产物目录里 rglob 到任意一个 `.js`/`.css`/`.html`/`.jar`/`.war`，就通过。

这意味着：
- 后端项目（只会产出 `.jar`/`.war`）和前端项目（产 `.js`/`.css`/`.html`）**共用一个"宽泛白名单"校验**
- 没有"后端必须有 .jar、前端必须有 .js"这种差异化硬约束
- 也没有"双端组件必须有 UMD 入口文件"这种类型专属校验

---

**总结**：

| 环节 | 是否按 project_type 差异化 |
|---|---|
| build 命令怎么跑（单 / 双端） | ✓ 有差异（dual 跑 2 次） |
| 产物目录在哪（`target` / `outputName` / `dist`） | ✓ 有差异 |
| **产物里放了什么才算有效** | **✗ 统一规则，只看扩展名** |

如果你想在第三层按类型做更严格的校验（比如 form-component-dual 必须有 `{outputName}.umd.min.js`，backend-api 必须有非 `.original` 的 `.jar`），可以加一层类型分派。要的话我来写。
