# ai-builder UED 优化审计与落地建议

> 日期: 2026-06-03  
> 范围: `/Users/mars/Vibe Coding/ai-builder` 前端产品体验、信息架构、视觉系统、交互状态与可用性。  
> 说明: 本文聚焦 UED 层面，不覆盖后端安全、数据库、部署和代码结构问题；涉及代码文件只作为定位依据。

## 1. 总体判断

ai-builder 已经从早期的“对话式生成应用”演化为一个复合工作台，当前承载了:

- AI Builder / AI Chat: 需求收集、标准设计文档、配置生成。
- 应用资产库: 应用列表、详情、成员、发布状态。
- 配置工作台: 模型、表单、列表、流程、权限、字典、页面等配置面板。
- 二次开发 / 自开发资产库: 在 AI Builder 内完成自开发组件、页面、工作区、IDE 打开、部署回应用。
- 平台管理: 租户、成员、平台环境、MCP、模型配置。
- Runtime / SPEC / Git / Proposal 等协作和发布能力。

功能能力已经很宽，但 UED 的核心问题是: **能力增长快于产品结构收敛**。用户进入系统后，不容易判断“我现在应该从哪里开始、当前处于哪条业务链路、下一步最重要动作是什么”。视觉上也存在多套 token 和多代设计痕迹混用，导致页面看起来都属于同一产品，但细节层级、间距、组件状态和暗色表现不稳定。

建议把后续 UED 优化从“继续美化页面”转为“重建工作流骨架”: 先收敛信息架构和阶段式主任务，再统一视觉系统，最后逐页做截图级验收。

## 2. 问题优先级

| 优先级 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| P0 | 主路径不清晰 | 新用户不知道从“建应用 / 改应用 / 二次开发 / 管平台”哪条路进入 | 重构一级导航和首页入口 |
| P0 | 核心工作台过载 | `ChatPage` 同时承载对话、文档、配置、部署、版本、变更计划，认知负担高 | 拆成阶段式工作台 |
| P1 | 视觉 token 混用 | 页面间圆角、阴影、色值、暗色层级不一致 | 保留一套主 token，另一套只做 legacy alias |
| P1 | 品牌命名混用 | “睿鲸AI”“aPaaS Builder”“AI Builder”并存 | 统一产品命名和导航文案 |
| P1 | 交互状态不完整 | loading/error/empty/disabled/focus 状态不统一 | 建立状态组件和页面验收表 |
| P2 | 暗色模式稳定性不足 | 嵌入平台、配置面板、代码区、对话区可能出现层级和对比问题 | 逐路由截图验收 |
| P2 | 页面性能感知偏重 | `ChatPage` 和主 bundle 偏大，进入核心页加载成本高 | 按工作区和面板做 lazy split |
| P3 | demo / 临时页面残留 | 产品导航和命令面板容易出现非正式入口 | 归档到 internal/dev routes |

## 3. 信息架构优化

### 3.1 当前问题

当前导航更像“功能模块清单”，而不是“用户任务路径”。例如:

- “首页”
- “应用资产库”
- “AI Builder”
- “自开发资产库”
- “平台管理”

这些名称从系统内部视角看合理，但对业务用户来说，它们不是清晰的任务动词。用户要完成的是:

- 从需求创建一个应用。
- 修改现有应用配置。
- 给应用加自开发页面/组件。
- 管理租户、成员、模型、平台环境。

### 3.2 推荐一级 IA

建议一级结构收敛为三条主线:

1. **建应用**
   - 新建应用
   - 上传/生成设计文档
   - AI Builder 对话

2. **改应用**
   - 应用资产库
   - 配置工作台
   - 变更计划
   - 部署历史
   - 二次开发

3. **管平台**
   - 租户与成员
   - 平台环境
   - 模型配置
   - MCP / 工具
   - Runtime / 发布链路

### 3.3 导航文案建议

| 当前文案 | 建议文案 | 原因 |
| --- | --- | --- |
| 首页 | 新建应用 | 首页不表达任务 |
| 应用资产库 | 应用 | 简短，符合资产入口 |
| AI Builder | 需求设计 | 降低产品名堆叠 |
| 自开发资产库 | 自开发资产 | 作为产物库，不作为独立创作入口 |
| 平台管理 | 管理 | 避免“平台”重复 |
| 设计文档 | SPEC / 设计文档 | 根据目标用户决定是否保留 SPEC |
| 运行与发布 | 发布 | 更接近用户动作 |

## 4. 核心工作流优化

### 4.1 建应用链路

推荐流程:

```text
选择创建方式
  -> 描述需求 / 上传设计文档
  -> AI 生成结构化设计文档
  -> 用户确认关键对象
  -> 生成配置预览
  -> 应用创建 / 部署
```

UED 要点:

- 第一屏只保留一个主 CTA: “开始创建应用”。
- 创建方式只保留 2 个:
  - 从需求描述创建
  - 上传设计文档
- 不要在第一屏同时展示模型、流程、权限、部署、二次开发等过多概念。
- 每一步需要明确“已完成 / 当前 / 下一步”状态。

### 4.2 改应用链路

推荐流程:

```text
选择应用
  -> 查看当前配置状态
  -> 选择改动范围
  -> 对话或表单编辑
  -> 生成变更计划
  -> 预览 diff
  -> 执行 / 回滚
```

UED 要点:

- 应用详情页应先回答三个问题:
  - 当前应用是否已发布?
  - 最近一次变更是什么?
  - 下一步最常用动作是什么?
- 配置面板不要默认全部铺开，按“数据 / 界面 / 流程 / 权限 / 发布”分组。
- diff 和变更计划要成为改应用链路的核心，不要只藏在某个抽屉里。

### 4.3 二次开发链路

推荐流程:

```text
选择应用上下文
  -> 选择自开发类型
  -> AI Builder 内部触发代码生成/修改
  -> 预览和调试
  -> 打包
  -> 安装回应用
```

UED 要点:

- 二次开发必须绑定应用上下文，不再提供独立 Coding 入口。
- 代码生成、文件修改、预览、调试都作为 AI Builder 的内部能力出现。
- 自开发资产库只管理产物和历史工作区；用户点开资产时直接打开 IDE。
- “工作区列表”和“代码生成对话”不要成为独立产品首页，避免用户误以为进入了另一个系统。
- 预览、调试、安装回应用是关键路径，应固定在页面高优先级区域。

## 5. 视觉系统优化

### 5.1 Token 收敛

当前存在多套变量体系:

- `frontend/src/styles/design-v3-tokens.css`
- `frontend/src/styles/theme-vars.css`
- 局部 Vue 文件中的 scoped 样式和旧变量引用

建议:

1. 确认 `design-v3-tokens.css` 为唯一主 token 来源。
2. `theme-vars.css` 只保留兼容 alias，不再定义新的品牌、阴影、字体、状态色。
3. 新增 lint/grep 规则:
   - 禁止新代码写 hex 色值。
   - 禁止新代码新增 `--t-*` 变量。
   - 禁止局部组件重新定义 brand/status 色。
4. 统一尺寸:
   - 页面标题: 24/32
   - 区块标题: 18/20
   - 正文: 14
   - 辅助信息: 12/12.5
   - 工具栏按钮高度: 30/32
   - 主要按钮高度: 36/40

### 5.2 色彩策略

建议主色仍保持企业蓝，但要控制蓝色泛滥:

- 蓝色只用于主操作、当前状态、链接、AI 进行中状态。
- 成功、警告、危险只用于状态，不用于装饰。
- 卡片背景应更多依赖 surface 层级，不要用大量 brand-soft 堆出层级。
- 图表/标签如必须多色，使用固定语义色，不随页面自由发挥。

### 5.3 卡片和面板策略

当前页面容易出现“卡片套卡片”和过多边框。建议:

- 页面级布局不要做浮动大卡片。
- 卡片只用于可点击/可选择/可拖拽对象。
- 配置编辑区优先使用左右分栏、表格、列表和 inspector，而不是每块都包卡片。
- 对话消息、工具调用、文件变更、命令输出可以保留卡片，但要区分层级:
  - 用户/AI 消息: 低边框、少阴影。
  - 工具调用: 紧凑行式。
  - 变更 diff: 高对比、可折叠。

## 6. 页面级优化建议

### 6.1 `Landing.vue`

目标: 从展示型首页转为任务入口。

建议:

- 第一屏只回答“你想怎么开始创建应用?”。
- 两个入口卡:
  - 描述需求
  - 上传设计文档
- 最近应用和最近会话放第二层。
- 平台设置、模型配置、MCP 不应出现在普通用户第一屏。

### 6.2 `Apps.vue`

目标: 应用资产库从列表页变成运营控制台。

建议:

- 卡片/列表切换保留，但默认应更偏密集列表，便于扫描。
- 每个应用突出:
  - 发布状态
  - 最近变更时间
  - 当前负责人/成员
  - 主要入口: 配置、继续对话、二次开发、发布历史
- 删除/历史/平台跳转放更多菜单，不抢主操作。

### 6.3 `ChatPage.vue`

目标: 从“大杂烩编辑器”拆成阶段式 Builder 工作台。

建议拆分为 4 个主要区域:

1. 左侧: 对话和意图输入。
2. 中区: 当前阶段产物，例如设计文档、配置预览、变更计划。
3. 右侧: Inspector，仅展示当前选中对象的属性和建议。
4. 顶部: 阶段进度和主 CTA。

推荐阶段:

```text
需求 -> 设计文档 -> 配置 -> 变更计划 -> 部署
```

每个阶段只保留一个主动作:

| 阶段 | 主动作 |
| --- | --- |
| 需求 | 生成设计文档 |
| 设计文档 | 确认并生成配置 |
| 配置 | 生成变更计划 |
| 变更计划 | 执行变更 |
| 部署 | 发布应用 |

### 6.4 二次开发能力

目标: 让二次开发成为 AI Builder 工作台内的能力，而不是独立 Coding 产品。

建议:

- 不再在主导航提供 `/coding` 入口。
- 从 AI Builder 的应用上下文进入二次开发，例如:
  - 给当前应用新增自定义页面。
  - 给当前表单新增自定义组件。
  - 调整已安装的自开发资产。
- 二次开发面板或 IDE 顶部固定显示:
  - 当前应用
  - 当前自开发资产 / 工作区
  - 自开发类型
  - 安装目标
- 自开发资产库中，点击资产不再进入 Coding 列表页，而是直接打开 IDE。
- 对话区、文件区、预览区采用 AI Builder 内部可调比例分栏。
- 命令输出默认折叠，只在失败时展开关键错误。
- 安装回应用要有明确的完成态和回到应用配置入口。

需要同步收敛的入口和文案:

- `/ide -> /coding`、`/coding`、`/extension-demo`、`/section-nav-demo` 不能作为公开产品入口。
- AI Builder、应用概览、运行发布页、扩展开发面板、自开发资产库里的“打开开发 / 去 IDE / AI Coding”按钮，需要统一为“在当前应用上下文打开 IDE”。
- “AI Coding / Vibe Coding / Coding 工作区”作为用户可见产品名应退出；可替换为“二次开发”“IDE 工作区”“自开发资产”。
- 如果短期保留 `/coding` 兼容路由，也应由 AI Builder 内部动作进入，且落地后看到的是当前应用、当前资产、当前安装目标，而不是一个独立 Coding 首页。

### 6.5 `WorkspaceCatalogPage.vue`

目标: 自开发资产库成为“可复用资产管理”，而不是独立 Coding 入口或工作区历史列表。

建议:

- 区分:
  - 工作中
  - 已安装到应用
  - 可复用资产
  - 失败/待修复
- 每个资产展示绑定应用、类型、最近构建状态、安装状态。
- 支持按应用、类型、状态过滤。
- 点击资产直接打开 IDE，进入对应工作区和文件上下文。

注意:

- `WorkspaceCatalogPage.vue` 当前已有直接打开 IDE 的方向，这是正确的。
- 列表动作文案建议从“进入开发”收敛为“打开 IDE”或“继续编辑”，避免重新制造独立 Coding 产品感。
- 如果自开发资产库不再是一级导航，它应挂在应用详情、AI Builder 二次开发阶段或管理里的资产入口下。

### 6.6 `PlatformAdminEmbed.vue`

目标: 嵌入平台管理时减少“双壳”感。

建议:

- 明确嵌入态和独立态的导航边界。
- 保证顶栏、侧栏、返回工作台行为一致。
- iframe/loading/error 状态必须统一样式。
- 暗色模式下检查 iframe 背景、边框、滚动条是否割裂。

## 7. 交互状态规范

每个页面至少需要覆盖以下状态:

| 状态 | UED 要求 |
| --- | --- |
| Empty | 告诉用户为什么为空，并给一个下一步动作 |
| Loading | 骨架屏优先于 spinner；超过 3 秒显示阶段文案 |
| Error | 错误文案要能指导修复；保留重试入口 |
| Permission denied | 说明需要什么角色，不要直接跳空白页 |
| Disabled | 说明禁用原因 |
| Success | 展示结果和下一步，不只 toast |
| Streaming | 明确“正在生成 / 可停止 / 已输出多少” |
| Long task | 30 秒以上任务要显示阶段和可离开提示 |

## 8. 暗色模式验收清单

重点路由:

- `/`
- `/apps`
- `/ai-chat`
- `/chat?app_id=...`
- AI Builder 内部二次开发面板 / IDE 打开态
- `/workspace-catalog`
- `/platform-admin`
- `/platform-envs`
- `/tenant-users`

检查项:

- 文本对比度是否足够。
- disabled 和 placeholder 是否过淡。
- 边框是否能区分 panel 层级。
- hover/focus 是否可见。
- Element Plus 组件是否被旧 token 覆盖。
- iframe 嵌入区域是否出现白边或黑块。
- 代码块、命令输出、diff 是否可读。
- Toast、Dialog、Drawer 背景是否与页面层级一致。

## 9. 响应式和空间策略

桌面端建议:

- 1440px 以上: 三栏工作台，对话 / 主画布 / inspector。
- 1200-1440px: inspector 可折叠。
- 900-1200px: 左侧导航收起，主区双栏。
- 900px 以下: 不建议完整承载配置工作台，提供查看和轻编辑；复杂编辑提示到桌面端。

移动端策略:

- 不追求完整低代码设计器移动可用。
- 移动端只保留:
  - 查看应用状态
  - 查看 AI 回复
  - 审批/确认变更
  - 查看部署结果
- 配置编辑、二次开发、流程设计默认桌面优先。

## 10. 可访问性与细节质量

建议补齐:

- 所有 icon button 必须有 `aria-label` 或可见文本。
- 交互元素统一 `:focus-visible`。
- 不要用 `div` 承载按钮行为。
- 命令面板、弹窗、抽屉要有 keyboard close 和 focus trap。
- 表单错误要贴近字段，不只 toast。
- 流式区域要避免自动滚动打断用户选择文本。
- 批量操作和危险操作必须二次确认。

## 11. 落地路线图

### Phase 1: 收敛主体验骨架

目标: 让用户知道从哪里开始、现在在哪、下一步做什么。

任务:

- 重命名和重组一级导航。
- 首页改为任务入口。
- 统一顶部品牌命名。
- 隐藏 demo/临时页面入口。
- 为建应用、改应用、二次开发三条路径补流程状态。

验收:

- 新用户 30 秒内能说出如何创建应用。
- 每个主页面有唯一主 CTA。
- 顶部和侧边栏品牌命名一致。

### Phase 2: 统一视觉系统

目标: 消除多代设计痕迹。

任务:

- 确认唯一主 token 文件。
- 清理旧变量和局部 hex。
- 统一按钮、卡片、表格、空状态、错误状态。
- 暗色模式逐页修正。

验收:

- 新代码不新增 hex 色值。
- 关键路由亮色/暗色截图通过评审。
- Element Plus 组件与自研组件视觉一致。

### Phase 3: 重构核心工作台

目标: 降低 AI Builder 工作台认知负担，取消独立 Coding 产品感。

任务:

- `ChatPage` 按阶段拆分: 需求、设计文档、配置、变更计划、部署。
- 二次开发能力下沉到 AI Builder 内部，并按应用上下文和工作区上下文打开 IDE。
- 工具调用、文件变更、命令输出做统一事件卡。
- diff / 变更计划提升为核心对象。

验收:

- 创建应用链路不需要用户理解所有模块。
- 修改应用链路能清楚看到差异和执行后果。
- 二次开发链路能闭环到“安装回应用”。

### Phase 4: 性能与感知优化

目标: 核心页面加载更快，长任务更可控。

任务:

- 拆分大 bundle。
- 配置面板按 tab 懒加载。
- 命令输出虚拟滚动或折叠。
- 长任务统一进度文案。

验收:

- 首屏进入应用资产库和首页无明显卡顿。
- 进入 AI Builder 时非当前面板不加载；二次开发 IDE 只在用户打开资产或触发开发动作时加载。
- 超过 10 秒任务有明确反馈，超过 30 秒可离开。

## 12. 验收方式

建议每次 UED 改动至少保留以下证据:

- 亮色桌面截图。
- 暗色桌面截图。
- 窄屏截图。
- 空状态截图。
- loading 或 streaming 状态截图。
- 错误状态截图。
- 关键路径录屏或 GIF。

关键路径:

1. 新建应用: 首页 -> AI Builder -> 设计文档 -> 配置预览 -> 创建应用。
2. 修改应用: 应用资产库 -> 应用详情/Chat -> 变更计划 -> 执行。
